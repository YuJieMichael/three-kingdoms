### Important R1：先生成营地后打听花鬘，位置互斥失效

**位置：** `faction-system.js:18`（新营地仍投影为wild且level=5），`faction-system.js:20–26`（阻止旧传闻占地，但既有营地被新传闻阻止推进）；定向关联 `hero-system.js:117–121` 的 `location/available`、`hero-system.js:143–154` 的实战俘获结算。

**触发：** 有一座合法副城 `city_wild_28_50`，官府5、客栈2、爵位2、已有首胜。真实开启势力后经过6小时，生产逻辑选中邻格 `wild_27_50` 建黄巾营地；其自然等级原为3，但营地公开叠加为5。随后执行正常 `HeroSystem.wild.discover()`，花鬘的首选坐标恰为(27,50)，当前 available 只检查wild/level/占领/其他传闻/有兵，因而在该营地生成花鬘传闻。全过程 `validSave=true`。

**实际后果，均已复现：**

- 不出征而继续经过6小时：首营地已到readyAt，却因新的active rumor被blockedTargets排除；没有预警，反而建立第二营地。只要该传闻仍活跃，首营地被持续阻止推进。玩家只是打听名将，就改变了已经开启的NPC进攻行为。
- 购花鬘画像并实际清剿：出征冻结守军为 `{militia:400,spear:150,archer:200}`，真实胜利同时俘获花鬘、发一个蛮族首俘箱并移除营地。俘获依据结算时的活传闻，战斗快照仍是势力营地；寻踪与营地两条玩法不再互斥。修正探针的整数时间后，保存和重载均正常，**不报告存档损坏**。

**最小修复：** 在在野名将选址的共用 available 判定中排除 `n.factionCamp`，使首次发现及位置迁移都与已存在营地互斥。新增“先营地→后发现”和“已派往营地→再发现”的回归，断言传闻选择其他合规野地、原营地仍可按期进入预警，清剿不会误俘该名将/发其首箱；保留“先传闻→后营地”现有测试。无需重写整个地图或名将系统。

**最短复现准备：** 使用 `loadGame(751)`；用现有 `CitySystem.empty` 建立真实平地 `wild_28_50` 的副城并记录conquered/wildOwners，切城后 `city(g,{hall:5,inn:2,drill:5,house:8,tavern:10})`，设置合法爵位2、首胜和测试所需库存。调用 `setFactionsEnabled(true, factionToggleQuote(true).key)`、`advance(21600000)`、`HeroSystem.wild.discover()`。可直接看到camp和huaman rumor同为wild_27_50。实战探针以 `advance(Math.ceil(expedition.end-now())+1)` 到达，5000弓兵真实逐回合结束，返回captured、barbarianEquipmentBox=1。

### Important R2：势力tick的中途保存穿透治疗和招募的整份回滚

**位置：** `engine.js:1367–1371` 的 `warCareTransaction`，`engine.js:1238` 的直接 `recruit`；共同原因在 `engine.js:508` 的势力tick落盘，以及 `engine.js:1448` 的外层事务名单未涵盖这些已承诺完整回滚的调用者。（以函数名为准：本审查HEAD为6a03a16。）

**触发：** 开启势力，并让 `Date.now()` 刚越过下一轮6小时时间，但尚未单独tick。执行已有伤兵的手动治疗（同样影响调用settle tick的自动治疗开关），或执行有合法客栈候选的直接招募。允许tick阶段的正常存档写入，在最终包含治疗/新将的写入处模拟浏览器存储失败。

**实际后果：** 新事务在tick前保存了一份内存副本，但tick创建营地时先保存了中间状态。最终写失败后只恢复内存副本，磁盘仍有中间营地/经济结算；同一个失败操作，留页与刷新看到不同状态。原“整个预操作状态已撤回”的合同不成立，后续重试保存与重载会沿不同状态继续。

两条独立定向探针都输出：

```text
error = 保存失败，已暂停操作。请导出当前进度后检查浏览器存储
memorySame = true
storedSame = false
memoryCamps = 0
storedCamps = 1
```

治疗探针另确认磁盘treated.archer仍为0；没有声称已复现免费兵或重复名将。问题是半份存档和回滚不一致，不能只用内存JSON相等来判通过。

**最小修复：** 让本轮新引入或承诺回滚的治疗/自动治疗及直接招募事务，在包含tick的整个操作期间禁止中途实际写入，只允许操作成功后一次最终落盘，并在失败时恢复本城投影连接。可复用现有事务深度/抑制保存机制，但无需泛化重构所有旧动作。新增到期势力tick与最终失败组合测试，同时断言完整内存、`sanguo-city-v2`存储字节、费用/伤兵/候选和来源城市状态；再覆盖最终成功只写入一份完整状态。

**复现核心：** `loadGame(751)`准备官府5、首胜与1e6测试黄金；`WarCare.admit(...,'npc:capital:1',{archer:10},Date.now())`；开启势力并保存，记录`JSON.stringify(g.state)`和`g.exportStoredRaw()`。把测试Date推进6小时而不tick；包装localStorage.setItem，在key为`sanguo-city-v2`且解析结果`warCare.treated.archer>0`时抛错，其余写入照常。调用`healWounded('archer',10,q.key)`即得到上述差异。直接招募版本把最终拒绝条件换为`generals.includes(candidate.id)`，其余步骤相同，同样复现。
